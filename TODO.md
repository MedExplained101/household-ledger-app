  **Real bugs found and fixed during Graham's first live-test attempt, 2026-08-01:** (1) the Google Maps Distance Matrix HTTP node's `Query Auth` credential wasn't attached at first, producing `REQUEST_DENIED`; (2) `Stores.address` was blank for the test stores, producing `NOT_FOUND` (needs a real street address per store, same category of manual fill-in as `home_address`); (3) `Missing Distance?`'s "is empty" string check threw on a genuine number once a store already had a real `distance_from_home_mi` — fixed by confirming `typeValidation: "loose"` (n8n UI: "Convert types where required") was actually on; (4) **the real find** — `Merge Catalog + Stores + Inventory`'s "Combine" mode with "All Possible Combinations" turned out to structurally support only 2 inputs in n8n — it kept silently collapsing back to 2 no matter how the third input was added, discarding the `Get Inventory` connection every time. Root cause: `Compute Recommendations` never actually read data from the Merge node's output in the first place — it pulls Catalog/Stores/Inventory entirely via named lookups (`$('Get Catalog')`, etc.), so the Merge node was only ever serving as a synchronization barrier, not a real merge. **Removed the Merge node entirely** and replaced it with a plain sequential chain — `Geocoding Done → Get Catalog → Get Stores → Get Inventory → Compute Recommendations` — applying the same fix pattern already used for the geocoding chain earlier the same day (named-node references only need the referenced node to have *run*, not to be *wired into* the current node's input). Also hit, unrelated to the workflow itself: a node-name collision (old nodes still on canvas when the updated JSON was pasted in, auto-suffixed "1" onto every colliding new node, breaking `$('NodeName')` references inside `Compute Recommendations` until the duplicates were deleted and names restored) — a reminder to fully delete old nodes before pasting a replacement workflow, not just paste on top.

  **(5) The sequential-chain fix above introduced its own bug, caught the same day:** standard n8n nodes (a Google Sheets "Get Row(s)" among them) default to running *once per input item*, not once total. Chaining `Get Catalog → Get Stores → Get Inventory` naively meant `Get Stores` re-ran once for every one of `Get Catalog`'s 312 items (312 × 4 real stores = 1248 output items — the math confirmed it exactly), and `Get Inventory` inherited that multiplied further; since `Inventory` is genuinely empty, 1248 × 0 = 0 total output, and n8n halts a branch that produces zero items — which is why `Compute Recommendations` never ran. Fixed by setting `executeOnce: true` on `Get Catalog`, `Get Stores`, and `Get Inventory` (all three, for consistency), which makes each read its sheet exactly once per workflow run regardless of upstream item count — the actual barrier behavior originally intended. No data was corrupted by this; it was purely an in-memory execution-count artifact, not duplicate writes to the Sheet.

  **(6) Once (5) was fixed, `Get Inventory` alone still halted the workflow** — with real per-item counts restored (Catalog 78, Stores 4), `Get Inventory` correctly executes once and finds `Inventory` genuinely empty (still true — nothing writes to it yet), which n8n treats as "0 output items" and halts the whole run right there, same class of issue as the Check-In Agent's "Get Stocked Items" node hit earlier the same day. Fixed the same way: added `alwaysOutputData: true` to `Get Inventory`, so an empty result propagates as a valid empty pass-through instead of stopping execution. `Compute Recommendations` already handles an empty `inventoryRows` correctly (zero recommendations, not an error).

  **(7) The same halt-on-zero-output issue recurred one node further downstream, at `Compute Recommendations` itself.** With `Inventory` genuinely empty, it correctly computes zero recommendations — but that's *also* zero output items, so n8n halted there too, meaning `Check For Recommendations` never got to run despite being written specifically to handle the zero case (its own comment said "a Code node in 'Run Once for All Items' mode always runs" — **that comment was wrong**, corrected in the file). Fixed by adding `alwaysOutputData: true` to `Compute Recommendations` as well.

  **(8) That fix had its own side effect, caught immediately after:** `alwaysOutputData` doesn't just prevent the halt — when a node's real output is empty, n8n substitutes a single placeholder item (`{}`) instead of truly zero items. `Check For Recommendations`'s old logic (`items.length > 0`) counted that placeholder as "1 item," so it wrongly reported `hasRecommendations: true` on a run with nothing to recommend — which then crashed `Format Recommendations Message` trying to `.map()` over the placeholder's nonexistent `items` field. Fixed by filtering to real recommendation objects specifically (`r.bulkStore` present) rather than raw item count. Verified with a standalone Node harness against three cases: the `{}` placeholder (correctly ignored), a real recommendation object (correctly counted), and true zero items (correctly handled) — all pass. With (6), (7), and (8) all in place, the workflow should now run end-to-end to the correct outcome: `Check For Recommendations` → `Any Recommendations?` (false) → `Nothing to Recommend This Week`, no Telegram message, no error.

  Still can't produce real recommendation output (though the pipeline itself now runs cleanly end-to-end): needs `Settings.home_address` filled in by hand (deliberately never committed — see `household-ledger-sheets-schema.md`), a Google Maps Platform API key credential (Distance Matrix API enabled, billing active — now wired), and real `Inventory.avg_days_to_finish`/`cycle_count` history, which only accumulates once the Check-In Agent has actually been running for multiple purchase cycles.

Because the node wasn't configured to tolerate failure, the entire execution halted before `Return List + Totals` ever ran — so *every* webhook call, including plain `{"action":"get"}` page-load requests that have nothing to do with budgets, came back empty. One broken alert node was silently taking down the whole app for everyone.

Two fixes, both applied and confirmed live 2026-08-08:
1. **`Check Budget Alert`'s "On Error" setting changed to Continue** — isolates alert failures from core list-loading, matching the sub-workflow's own documented "fire-and-forget" design intent (which had never actually been configured this way). Confirmed immediately: the app's Network tab response body went from empty to a full, valid list JSON, and the OFFLINE banner cleared.
2. **Root cause of the `budget` type error, fixed separately:** `Compute Totals` outputs a correct numeric `budget` (verified: `Number(settings.budget) || 0` → `200`), but `Check Budget Alert`'s Workflow Inputs mapping was receiving it as the string `" 200"` (leading space) rather than a native number, failing the sub-workflow trigger's strict `number` type validation. Fixed by enabling **"Attempt To Convert Types"** on `Check Budget Alert`'s Workflow Inputs. Confirmed live: pushed the list back over budget through the real app, `Check Budget Alert` succeeded (`"ok": true`), and the Telegram alert was actually delivered to Graham — completing the Budget Alert Listener's live-test checklist item above.

**Check-In Agent + Reply Listener — first live-test attempt, two real bugs found (both fixed in the repo, not yet reverified end-to-end).**

1. Triggered `Household_Ledger_CheckIn_Agent.json` manually; the check-in question reached Telegram, and the reply (`LOW: sugar,milk,mealiemeal` / `FINISHED:cooking oil, rice`) was parsed correctly by the Reply Listener's `Parse Reply` node despite messy spacing/commas. But `Call Resume Webhook` 404'd: `"The workflow for execution \"9734\" does not contain a waiting webhook with a matching path/method."` Root cause: `Wait for Check-In Reply` in the Check-In Agent had never had its `httpMethod` explicitly set — silently defaulting to `GET` — while `Call Resume Webhook` (correctly) sends a `POST`, since it needs to carry a JSON body (`lowItems`/`finishedItems`). n8n's Wait-node resume matching requires both path *and* method, so every resume attempt was doomed regardless of how correctly everything upstream parsed. This wasn't a live-vs-repo drift like the other bugs tonight — the checked-in JSON had the same implicit-GET gap since the workflow was first built; it just took a real end-to-end test to surface it. Fixed by adding explicit `"httpMethod": "POST"` to the `Wait for Check-In Reply` node.

2. After the GET/POST fix, the resume itself worked, but both downstream parallel branches (`Compute Inventory Updates` and `Resolve Auto-Add Rows`) died silently with "No output data returned," leaving `CheckIn_Status` stuck on `pending` and `Send Confirmation`/`Clear Pending State` never running. Two compounding causes: (a) `Compute Inventory Updates` only updated items that *already existed* in `Inventory` — since `Inventory` starts genuinely empty, every item's first-ever mention was silently dropped, making `Update Inventory Rows`' `appendOrUpdate` mode (added 8/1 specifically for this case) unreachable in practice; (b) neither Code node had `alwaysOutputData` set, so a genuinely-empty result (e.g. none of the replied item names matching an exact `Catalog` entry — correct, intentional behavior for `Resolve Auto-Add Rows`) halted the branch entirely instead of passing through, same failure class already hit three times in the Recommendation Agent (see 8/1 entries above). Fixed: `Compute Inventory Updates` now creates a fresh zero-history row for first-time items instead of skipping them; both Code nodes got `alwaysOutputData: true`; two new IF gates (`Has Inventory Updates?`, `Has Auto-Add Items?`) inserted before the two Sheets-write nodes so the `alwaysOutputData` placeholder can never be written as a blank row — both gates route their false branch straight to `Merge Both Branches` so confirmation/cleanup still always runs.

Both fixes are in the repo; still needed live in n8n: apply the `httpMethod` change, the code/settings/gate-node changes described above, cancel/let the stuck execution expire (48h limit), and re-run the full test (trigger → Telegram question → reply → confirm `Inventory`/`ShoppingList` actually update) to close out this checklist item — not yet reverified end-to-end. Note: a fuller test of the auto-add-to-`ShoppingList` path specifically needs a reply using an *exact* Catalog item name (e.g. `FINISHED: Eggs`) — tonight's casual test names (`sugar`, `milk`, `rice`, etc.) don't match this catalog's curated naming, which is correct skip behavior, not a bug, but means that path is still functionally unverified.
